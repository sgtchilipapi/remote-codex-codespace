# Observable failure signals

Research completed 2026-09-10 against the repository, Codex app-server documentation and the schema generated by the installed `codex-cli 0.153.4`, GitHub Codespaces/CLI documentation, the Fetch standard, and Node.js child-process documentation.

## Finding

The desired attribution is possible only when each boundary preserves the structured signal it owns. The Mobile Client can reliably distinguish its own validation/decoding failures, a connection failure, and a Relay HTTP response. The Relay can reliably identify its own authentication, validation, conflict, capacity, retention, and buffer failures. Codex exposes a typed Turn-error taxonomy and an explicit retry-in-progress bit. By contrast, the Relay's single `gh codespace ssh … codex app-server --stdio` child conflates GitHub CLI, GitHub authentication/API, Codespace state, SSH, remote shell, missing Codex, and app-server exit. A generic child exit must therefore remain an unknown upstream disconnect unless a separate authoritative Codespace probe or a preserved structured Codex message establishes a deeper source.

This yields a strict attribution rule: use the deepest structured signal actually observed, never infer a component from the operation being attempted, HTTP status alone, human-readable stderr, or elapsed time.

## Signals by boundary

| Boundary | Reliably observable signal | Safe attribution and condition | Limit |
| --- | --- | --- | --- |
| Mobile Client before fetch | Empty token and configuration values checked against the loaded model/reasoning/permission/tier catalog | `mobile_client`: local validation, including a missing Relay token or locally unsupported configuration | A catalog can become stale; a later rejection is not the same condition. |
| Mobile Client → Relay | Fetch fulfills with an HTTP response versus rejects with a network error | Fulfilled response proves the Relay HTTP boundary replied. Rejection supports only `connection`: Relay not reached | The Fetch API intentionally exposes many DNS, TCP, TLS, CORS, offline, and server-unreachable cases as a network error; it cannot establish which component failed. [WHATWG Fetch, network errors](https://fetch.spec.whatwg.org/#concept-network-error) |
| Relay response decoding | Invalid JSON, invalid NDJSON, missing required envelope fields, invalid event sequence/type | `relay`: malformed response, when an HTTP response/body came from the Relay; `mobile_client`: unsupported client-side state only when the response itself satisfies the agreed contract | Today several paths either do no shape validation or collapse parse and transport failures into the same prose. |
| Relay request gate | Missing/mismatched configured bearer token; input bounds; malformed IDs/cursors; unsupported configuration; stale configuration revision; conflicting active Turn; missing/expired retained Turn; subscriber limit; output buffer limit | `relay`: authentication rejected, validation failed, conflict, retained Turn unavailable, capacity exceeded, or output too large | The current Relay uses one `401` for both an absent server-side `API_TOKEN` and a mismatched client token, so it cannot safely say which configuration side is wrong. |
| Relay timers | Initialization timer or per-request timer expires | `relay`: upstream operation timed out | Timeout identifies the enforcing boundary, not whether GitHub, SSH, the Codespace, or Codex caused the delay. It must not be labelled “Codex timed out” without a Codex signal. |
| Relay child-process lifecycle | Spawn `error`; child `close(code, signal)`; stderr bytes | Spawn failure can be `relay`: GitHub CLI could not be launched. A child exit proves the composite upstream transport ended | Node exposes spawn failure separately and `close` with exit code/signal, but the current handlers discard code, signal, and stderr. A spawned `gh codespace ssh` child's nonzero exit can arise before SSH, inside SSH, or from the remote `codex` command. [Node.js child-process events](https://nodejs.org/api/child_process.html#event-error) |
| GitHub CLI | Exit `0`; nonzero exit; termination signal | `0` establishes successful completion of the composite command; a signal establishes local cancellation/termination | Although `gh` documents general codes `1` (failure), `2` (cancelled), and `4` (authentication required), `gh codespace ssh` runs a remote command and documents no command-specific exit contract. A composite exit code therefore cannot safely identify which layer produced it. Stderr phrases must remain diagnostic-only. [GitHub CLI exit codes](https://cli.github.com/manual/gh_help_exit-codes), [`gh codespace ssh`](https://cli.github.com/manual/gh_codespace_ssh), [`gh codespace ssh` source](https://github.com/cli/cli/blob/trunk/pkg/cmd/codespace/ssh.go) |
| Codespace state | A separate successful `gh codespace view --json state` or Codespaces REST read can return the named Codespace's state; REST separately returns `401`, `403`, `404`, and `500` | `codespace`: confirmed non-running state, not found, GitHub authentication required, forbidden, or GitHub service failure, using the probe's structured result | The current Relay does not perform this probe. A successful state read does not prove SSH or the remote command works. [`gh codespace view`](https://cli.github.com/manual/gh_codespace_view), [Codespaces REST: get a Codespace](https://docs.github.com/en/rest/codespaces/codespaces#get-a-codespace-for-the-authenticated-user) |
| Codespace diagnostic | `/test` runs `hostname && pwd` over a fresh SSH child | Success proves that the named Codespace accepted this SSH command at that moment and provides its remote output | Its current nonzero result is the same composite `gh` failure and cannot distinguish stopped/missing Codespace, GitHub auth/API, SSH server, remote shell, or command failure. It is not a Codex health check. |
| App-server startup | Valid `initialize` response; JSON-RPC error response; malformed stdout JSON; initialization timeout; child exit | Successful initialization establishes that Codespace, SSH, remote command launch, app-server framing, and handshake worked at that moment. A well-formed JSON-RPC error is `codex` request rejection. Malformed stdout after launch is a Codex-protocol failure if the transport is otherwise established | Timeout and pre-handshake child exit do not identify the failing upstream component. Current code discards the JSON-RPC error object and maps all of these to catch-alls. |
| App-server request/response | JSON-RPC error `{code,message,data?}` correlated by request ID | `codex`: protocol/request rejection. Stable codes currently include `-32600` invalid request, `-32601` method not found, `-32602` invalid params, `-32603` internal error, and `-32001` overload | Only `-32001` has documented retry guidance. `-32600` covers multiple domain conditions, and `data` is unconstrained/usually absent; code plus prose is insufficient to distinguish missing Thread, config failure, model failure, or other domain causes. [Codex error-code source](https://github.com/openai/codex/blob/main/codex-rs/app-server/src/error_code.rs), [Codex app-server transport and schema](https://developers.openai.com/codex/app-server/#message-schema) |
| Codex Turn lifecycle | `error` notification with `error` and `willRetry`; terminal `turn/completed` with `status` and optional `turn.error` | `codex`: typed Turn condition; `willRetry` says Codex itself is retrying the current Turn. Terminal `failed`, `interrupted`, and `completed` are distinct outcomes | `willRetry` does not authorize the Mobile Client to replay `turn/start`. Terminal failure may lack typed info; then only `codex/other` or unknown Codex failure is justified. [Codex app-server errors](https://developers.openai.com/codex/app-server/#errors) |
| Codex account/quota state | `account/rateLimits/read` / updates include usage windows and, in the installed schema, `rateLimitReachedType` and `spendControlReached` | `codex`: account limit state when those structured fields are present; typed Turn errors separately distinguish usage/rate/session-budget limits | Missing/null account fields mean unavailable, not “within quota.” A failed account read is merely a failed Codex request unless its JSON-RPC error is more specific. |
| Turn event transport to Mobile Client | Relay event sequence and retained replay; early EOF/read rejection; HTTP `404` after retention; HTTP `429` subscribers | `relay`: retained Turn unavailable or subscriber capacity when an envelope says so. Early EOF/read rejection supports `connection`/stream interrupted, not Codex failure | The Turn continues after a subscriber disconnect, so the Mobile Client may reconnect by Turn ID and last sequence. It must not restart the mutating Turn. |

## Codex-specific condition inventory

The installed v2 schema's `CodexErrorInfo` is a genuine machine-readable discriminator. Preserve its camel-case wire values and map them into the Relay's stable vocabulary rather than parsing `message` or `additionalDetails`:

| Upstream `codexErrorInfo` | What is established | Retryability established by the value alone? |
| --- | --- | --- |
| `contextWindowExceeded` | Context capacity exhausted | No |
| `sessionBudgetExceeded` | Thread/session budget exhausted | No |
| `usageLimitExceeded`, `rateLimitExceeded` | Account/workspace usage or rate limit reached | No; use `willRetry` for the current Turn and rate-limit reset data for future action |
| `serverOverloaded` | Codex upstream overloaded | No by itself; `willRetry` is authoritative for the running Turn |
| `unauthorized` | Codex authentication rejected | No |
| `badRequest` | Codex/upstream rejected the Turn request | No; not specific enough to call it a model or configuration error |
| `httpConnectionFailed { httpStatusCode? }` | Codex failed an upstream HTTP request | No; the nested status adds evidence but does not by itself make replay safe |
| `responseStreamConnectionFailed { httpStatusCode? }` | Codex could not connect to its model-response stream | No; consult `willRetry` |
| `responseStreamDisconnected { httpStatusCode? }` | Codex's model-response stream broke mid-Turn | No; consult `willRetry` |
| `responseTooManyFailedAttempts { httpStatusCode? }` | Codex exhausted its own response retry attempts | Terminally not retrying this Turn; a new user retry is still an operation-policy decision |
| `activeTurnNotSteerable { turnKind }` | Turn input conflicts with a review/compact Turn | No |
| `sandboxError` | Codex sandbox setup/execution failed | No |
| `threadRollbackFailed` | Codex Thread rollback failed | No |
| `cyberPolicy`, `misalignmentPolicyViolation` | Codex policy stopped the Turn | No |
| `internalServerError` | Codex internal failure | No |
| `other` or null | Codex reported a failure without a stable subtype | No; do not infer from message |

The published documentation currently lists a subset of these values; the complete set above comes from the schema generated by the installed CLI. Codex documents that generated schemas match the generating version exactly. [Codex app-server schema generation](https://developers.openai.com/codex/app-server/#message-schema)

## Current collapse points

The implementation currently removes most of the usable evidence:

- [`AppServerConnection.handle`](../../../../server.js#L31) replaces every JSON-RPC `error` object, including its code and data, with `Error("Codex request failed")`.
- The child `close` handler at [`server.js`](../../../../server.js#L24) ignores exit code and signal; no handler reads stderr. This erases useful diagnostic lifecycle detail, while the remaining generic close makes SSH/Codespace/Codex launch failures indistinguishable for public attribution.
- Startup parse, spawn, close, and timeout failures are all funneled through the same connection teardown. The route wrapper at [`server.js`](../../../../server.js#L214) preserves only selected Relay HTTP statuses and rewrites almost everything else to `Codex unavailable`; it incorrectly attributes Relay-enforced timeout as `Codex timed out`.
- Turn startup catches every exception and emits only `Codex unavailable` ([`server.js`](../../../../server.js#L315)). App-server `error` notifications are not handled at all; their `codexErrorInfo`, `additionalDetails`, and `willRetry` disappear. Terminal `turn.error` is also dropped, and `interrupted` is rewritten to `completed` ([`server.js`](../../../../server.js#L347)).
- App-server disconnect during a Turn becomes the same `Codex unavailable`, even though the composite SSH child does not prove Codex was the component that failed ([`server.js`](../../../../server.js#L363)).
- Relay buffer overflow is internally distinguishable but sent as free text in the same generic Turn `error` event; the envelope has no source, code, retryability, or diagnostic identity ([`server.js`](../../../../server.js#L293)).
- Status catches every rate-limit read failure and emits only `rate_limits/upstream_unavailable/retryable: true`; when no cached snapshot exists, the route collapses again to `Codex unavailable` ([`server.js`](../../../../server.js#L247)).
- `/test` calls every nonzero composite SSH outcome `Codespace unavailable`, though it cannot distinguish the GitHub API, credentials, Codespace state, SSH, remote shell, or command ([`server.js`](../../../../server.js#L277)).
- The Mobile Client's Settings path conflates a browser network failure with Relay/Codespace unavailability and conflates every Relay `502` the same way ([`public/client.js`](../../../../public/client.js#L509)). Thread list, resume, history, reload revalidation, and Status each replace HTTP/envelope/parse detail with screen-specific catch-alls; reload revalidation additionally clears the saved Thread on any failure, not only confirmed absence ([`public/client.js`](../../../../public/client.js#L174), [`public/client.js`](../../../../public/client.js#L297), [`public/client.js`](../../../../public/client.js#L576), [`public/client.js`](../../../../public/client.js#L846)).
- The Turn client reduces retryability to `HTTP >= 500`; a fetch or NDJSON parse failure has no typed source, all such failures loop as “Connection lost,” `429` is considered non-retryable, and the stale-configuration branch parses English prose ([`public/client.js`](../../../../public/client.js#L969), [`public/client.js`](../../../../public/client.js#L1032)).

## Required uncertainty boundaries for the specification

- Do not distinguish browser offline, DNS, TLS, CORS, Railway routing, or Relay process outage from a rejected fetch. The stable condition is only `connection/unreachable`.
- Do not distinguish stopped/deleted Codespace, GitHub authorization/API failure, SSH failure, missing remote binary, or app-server crash from a generic nonzero `gh codespace ssh` exit. Keep an unknown upstream/connection condition, then attach a separate state probe result if one exists.
- Do not call an enforced timeout a Codex timeout. Record which boundary timed out and leave the underlying source unknown.
- Do not infer missing Thread, bad configuration, unsupported model, or authentication from JSON-RPC `-32600`/`-32603` prose. Preserve request method and upstream code for diagnostics; expose a narrower user condition only when a dedicated structured discriminator exists.
- Do not derive automatic replay from HTTP class or Codex error type. `ErrorNotification.willRetry` describes Codex retrying the existing Turn; Mobile Client replay safety belongs to the operation/recovery contract.
- Do not treat item-level `error` content alone as the Turn outcome. The terminal Turn status is authoritative; item errors remain transcript content unless the terminal lifecycle says the Turn failed.
- Do not expose raw `message`, `additionalDetails`, stderr, command, path, upstream body, or JSON-RPC `data` without an explicit sanitizer. They are diagnostic inputs, not user-safe contract fields.
